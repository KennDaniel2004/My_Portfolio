01

I Don't Build Alone — I Build With the Right Tools

I'm not a developer who writes every line from scratch. I turn ideas into working applications by combining programming knowledge, problem-solving, research, design, and modern AI-assisted development.

Before I write a single line of code, I try to understand the problem, study how similar systems work, and spend time designing and refining the concept in Figma. Good development starts before development starts.

The Goal

Turn ideas and problems into useful, maintainable applications.

02

AI Is a Tool. Understanding Is My Responsibility.

ChatGPT Claude DeepSeek GitHub Copilot And many more AI tools

I use these tools to explore ideas, understand unfamiliar technologies, generate implementations, troubleshoot problems, and speed up repetitive work — they help me move faster, they don't decide what ships.

Every generated output goes through the same routine: I review it, understand the implementation, test it, adapt it to the project, and decide whether it's actually appropriate. If it isn't, I rewrite it.

AI can generate code.
I am responsible for understanding what that code does.
03

Every Application Starts With a Problem

Before any code gets written, I work through five questions, in order.

  1. 01

    Understand

    What problem am I solving?

  2. 02

    Research

    What technologies and approaches could solve it?

  3. 03

    Design

    What should the user experience?

  4. 04

    Plan

    How should the application be structured?

  5. 05

    Build

    How should the solution be implemented?

04

I Design the Experience Before I Build the System

Every project starts in Figma, not in an editor. I sketch layouts, map the user flow, and go through several rough passes before anything is considered final. Design isn't a step I skip to save time — it's what keeps the application usable once it's built.

I revisit the same screens repeatedly, questioning spacing, hierarchy, and flow until the interface feels obvious to use.

Explore → Refine → Validate → Build
05

Working Code Is Not Always Good Code

School is where I first learned that architecture matters as much as logic. I separate responsibilities instead of putting everything in one file — MVC, a service layer, a DAO, clear separation of concerns, and reusable components.

User Interface
Controller
Service
DAO / Data Access
Database / API

The goal was never more files — it's giving each part of the system a clear responsibility, so any piece can change without breaking the rest.

If a project becomes difficult to understand, I look for ways to simplify its structure.

If It Works, I Still Ask: Can It Be Better?

  • Does it solve the actual problem?
  • Is the implementation correct?
  • Is the architecture understandable?
  • Is unnecessary code removed?
  • Can another developer maintain it?
  • Does the application provide a good user experience?
